# AUDIT.md — the painting report

You asked, using the painting analogy: are the only two white holes the **admin overlay** and
**Hyperframes**, are there any **blackened spots** (templated elements), and are there any
**misaligned colors** (inconsistencies/incorrectness)? This file is the honest, exhaustive
answer, audited against the code on **2026-08-19**. Short version: the backend, database and
data fetching are **real, not scaffolding** — every screen talks to live Firestore and the
deployed `lokidxb.com` APIs. Your two known white holes are real and are joined by two smaller
ones (Google OAuth and desktop-only layouts). The blackened spots that exist were **inherited
from the website itself** (they are templated on the web too, so the port reproduces them
faithfully). The misaligned colors are a short list of mobile-platform adaptations and
approximations, each described below; one genuine bug (deep links in Expo Go) was found during
this audit and has already been fixed.

---

## Part 1 — Is the paint real? (backend / database / data fetching)

### Places, categories, and explore filters — REAL
The `places` grid, search, vibe albums, explore taxonomy and map markers all come from live
Firestore reads: `fetchPlaces()` queries the `places` collection, `fetchCategories()` reads
`config/categories`, and `useExploreGroups()` merges the built-in taxonomy with admin-added
sub-filters from `config/exploreSubfilters` — the same documents the website reads. Expired
pop-ups are filtered with the exact same date logic as the web (`isExpiredLimitedTimePopup`).
Nothing here is seeded, mocked or hardcoded; if the website's data changes, the app changes.

### Accounts and auth — REAL
Sign-in/sign-up go through the real Firebase Auth project (`loki-bc0bb`) with sessions persisted
in AsyncStorage, and account creation calls the deployed `POST /api/create-account` (with a
direct-Firestore fallback that mirrors that route's logic). User documents are keyed by email in
the shared `users` collection, so anything done in the app is visible on the website and vice
versa. The only auth *method* difference is Google OAuth, covered as a white hole below.

### Collections CRUD, sharing, voting, live locations — REAL
Creating/deleting collections and adding/removing places write to `users/{email}` with the same
document shapes as the web (including the shared-collection dual-write to `sharedCollections`
docs and the owner's copy). Share links are generated by the real `POST /api/encrypt`, resolve
through `POST /api/decrypt`, and the shared-collection page uses the real
`/api/shared-collection/save|mutate|vote|search-places` routes. Swipe-to-decide votes and live
participant locations persist through `lib/collectionPersistence.ts`, a line-for-line port of the
web module, writing to the same Firestore sinks.

### Ask Loki chat, geocoding, uploads — REAL
The chat posts conversation history to the deployed `POST /api/gpt` and renders its real answer
plus recommendation cards; the maps "go to any area" search hits `GET /api/geocode`; the Trial
page uploads through Firebase Storage (`uploadBytesResumable`) with a real progress bar and
returns a real download URL. There are no stubbed responses anywhere in the app — every network
call in the codebase targets the production backend or Firebase directly.

### What has NOT been machine-verified — on-device runtime QA
TypeScript is clean, expo-doctor is 18/18, both platform bundles compile (3,486 modules), the
SDK-54 manifest is correct, and the embedded WebView scripts are syntax-checked — but no machine
can tap through the app on a physical phone. The tap-through checklist in `HUMAN_STEPS.md`
Part 3 is the remaining verification layer, and it can only be executed by you. Until you run
it, "works end to end" is verified at the compile/logic/API-contract level, not the
finger-on-glass level.

## Part 2 — White holes (missing paint)

### The admin overlay (known hole #1)
The entire `/admin` suite — admin login, dashboard (Add/Edit/Pending Places, categories,
explore-filter management, CSV import/export), agent and devin pages — does not exist in the
app in any form. This was your explicit scope decision on 2026-08-15, and nothing in the app
pretends to offer it (there are no dead admin buttons; the admin-only "Delete Place" button in
place details was deliberately not ported). Filling this hole would mean porting ~10 web pages
plus cookie-based admin session handling to the app.

### Hyperframes (known hole #2) — and its seven visible cutouts
You chose to remove Hyperframes entirely, and this hole touches seven concrete spots that exist
on the web: the welcome flash after first sign-in, the "collection created" flash (three call
sites), the vibe-applied flash, the "See what's possible" story button on the empty collections
state, the "Watch your recap" glass button + recap icon button in the collection detail view,
the (already commented-out on web) Loki Wrapped card on the profile, and the profile-reveal
composition at the end of the onboarding quiz. In the app those moments either show only the
toast (flashes), are simply absent (recap buttons, story button), or skip straight to the next
step (onboarding advances to "You're all set" when the progress bar finishes instead of playing
a 7.5-second composition). Everything around these cutouts is functional — the underlying
actions (create, vote, apply vibe, finish quiz) all work.

### Google OAuth (small hole, platform-imposed)
The website signs users in exclusively with a Google popup; the app uses email/password because
`signInWithPopup` does not exist on React Native and native Google Sign-In cannot run inside
Expo Go. The replacement is fully functional against the same Firebase user pool, but it is a
different *method* than the web, and an email already registered via Google on the website
cannot create a password login with the same address. Filling this hole requires leaving Expo
Go for a development build and adding `@react-native-google-signin/google-signin`.

### Desktop-only layouts (deliberate non-goal)
The port targets the web's **mobile breakpoint**, so desktop-only UI was intentionally not
painted: the dashboard's left sidebar with the collection list and "Add Collection" dialog, the
maps page's side-by-side list/details column with its maximize/minimize buttons, and the
Authentication page's two laptop side panels. On a phone-sized viewport the website itself never
shows these, so the app matches what a phone user of lokidxb.com actually sees. If you ever want
tablet layouts, this is where new canvas would be needed.

## Part 3 — Blackened spots (templated elements)

### The Plans page is fake — on the web too
`/dashboard/plans` renders hardcoded "Plan Title 1 / Plan Title 2", fabricated dates
("2024-01-20"), "Skydiving Adventure"/"Desert Safari" idea cards, and View/Add buttons that do
nothing — because the **website's** plans page is exactly this placeholder. The app reproduces
it verbatim for parity, so this blackened spot is a faithful copy of a blackened spot in the
original painting. If Plans ever becomes a real feature on the web, the app screen needs the
same real implementation.

### Profile's "Help & Support" and "Suggest a Venue" are no-ops — on the web too
Both rows render, animate and press correctly but their handlers are empty (`onPress: () => {}`),
which is a 1:1 copy of the website's `onClick: () => {}`. The same applies to the "⋯" (More)
button in the collection detail header, which has no handler on the web either. These should
stay empty until the website gives them behavior, at which point the app should mirror it.

### Ambassadors all share one photo — on the web too
The three ambassador cards (Nyla, Jade, Manav) all display the same bundled `ambassador.png`
because the website points all three at the identical `/ambassadors/image.png`. Names,
universities, Q&As and Instagram links are real and tappable. When real photos land on the web,
drop them into `assets/web/` and point each card at its own file.

### The Maintenance "Team access" form works but its result is meaningless in-app
The form genuinely POSTs to `/api/maintenance-bypass` and surfaces real success/error responses,
but the thing that endpoint produces — a signed browser cookie that unlocks the website — has no
effect inside a native app. It exists because you asked for every page, and the page is a
faithful replica; just know that "Enter the app" succeeding changes nothing in the mobile app
itself. This is cosmetically complete, functionally web-only.

### Dead code carried over or left behind (harmless, worth knowing)
Three things exist but are never used: `assets/web/Google.png` (copied for the auth page before
the Google button was dropped), `createCollectionShareLink()` in `lib/crypto.ts`
(CollectionsScreen calls `/api/encrypt` directly instead), and the `API_ENDPOINTS` map in
`constants/apiEndpoints.ts` (screens use `WEB_BASE_URL` directly). The collections screen also
keeps the web's dead `swipe` state (set by the "Swipe style" add option but read by nothing —
identical dead state exists in the web source) and an unused `Loader2` import. None of these
affect behavior; they are dust on the frame, removable any time.

## Part 4 — Misaligned colors (inconsistencies & corrections)

### Deep links in Expo Go — was a real bug, FIXED during this audit
The navigation config originally listed only `loki://` and `https://lokidxb.com` as link
prefixes, but inside Expo Go incoming links arrive as `exp://<host>:8081/--/<path>`, so the
shared-collection deep link could never have matched — and `HUMAN_STEPS.md` gave instructions
that wouldn't work. `expo-linking` is now installed, `ExpoLinking.createURL('/')` was added as
the first prefix, and HUMAN_STEPS 3.5 was rewritten with the correct `exp://…/--/collection/<token>`
form. Note the related limitation: tapping an `https://lokidxb.com/collection/…` link opens the
website, not the app — universal links into a native app require a store/dev build with
associated-domain entitlements, which Expo Go cannot have.

### Toasts can be hidden behind open modals
Sheets, drawers and dialogs in the app are native RN `Modal`s, which always render above
everything — including the sonner-native Toaster mounted at the root. So a toast fired while a
modal is open (e.g. "Added to collection" while the place-details sheet is still up) is invisible
until that modal closes, whereas on the web sonner floats above everything. The actions
themselves complete fine; only the confirmation banner is late. A future fix is to render a
Toaster inside modal content or replace RN Modals with plain animated views.

### The maps interstitial shows once per session, not once per visit
On the website every navigation to `/dashboard/maps` remounts the page, so "You are now entering
maps" appears on every visit. In the app the Maps tab stays mounted, so the interstitial appears
only the first time per app launch (and again if a `?place=` deep link forces entry). This is
arguably better UX but is technically a behavioral divergence; if you want strict parity, reset
`mapsEntered` on tab blur.

### The "limited-time popup" pulse only animates on the map, not in native lists
The web gives active pop-up places a pulsing red `box-shadow` animation
(`place-popup-active-now`) everywhere. Inside the map WebView that exact CSS animation runs on
markers and popup cards, but on native list/grid cards (browse search results, vibe grids,
sheet rows) the app renders a **static** red border/glow instead of the 2.2-second pulse loop.
Same signal, same color, no animation — an intentional simplification that could be upgraded
with a small Reanimated loop.

### Toast position: bottom-center instead of bottom-right
The website mounts sonner at `bottom-right`; sonner-native only offers center-aligned positions,
so the app uses `bottom-center` with the same dark rich-colors theme. On a phone-width viewport
the difference is a few dozen pixels of horizontal alignment. Cosmetic only.

### Animation approximations (glows, gradients, rays, carousels)
The signature ambient effects are re-creations, not the same engine: framer-motion's
per-segment eased keyframes became linear-progress interpolation through the same keyframe
values, CSS radial-gradients became SVG radial gradients, the `animate-gradient`
background-position trick became a translating LinearGradient under a text mask, and the
blur-heavy light rays use soft gradient falloffs because native views have no cheap gaussian
blur. Timings, colors, opacities and choreography all match the web values; under a magnifying
glass the easing curves and blur edges are approximations. The editorial 3D carousel and swipe
deck use the same math as the web (wrap/rotateY/threshold constants copied verbatim).

### Font fidelity at the edges
Geist, Geist Mono and Outfit load from the same Google Fonts sources the site uses, and every
Tailwind size/tracking was converted numerically — but the serif italic (`font-serif`) resolves
to Georgia on iOS and Noto Serif on Android, which is exactly how Tailwind's default serif stack
behaves in browsers but means the "Loki"/"Collections" hero glyphs differ slightly per platform,
as they do across browsers. Inside the map WebView, popup text loads Geist from the Google Fonts
CDN and falls back to system sans while offline. This is parity-with-the-web's-own-variability,
not a defect.

### The map WebView needs the network to boot
MapLibre GL JS and its CSS load from unpkg, the basemap style/tiles from Carto, exactly like the
website — but the website additionally *bundles* its own maplibre JS, whereas the app's WebView
fetches it at map open. With no connectivity the map screen stays on the blurred "Loading map…"
overlay (the rest of the app still works, and Firestore serves its offline cache). If you ever
want offline-proof map boot, the maplibre JS could be inlined into `maplibreHtml.ts`.

### Active-marker ring geometry
The web's selected marker uses Tailwind `ring-4` with a 2px transparent ring-offset, letting the
map show through a 2px gap before the rose ring; the WebView emulation draws the rose
box-shadow from the border outward with no transparent gap. The selected state is equally
obvious, the halo is simply 2px "tighter" than the browser's. Sub-pixel-level nitpick, recorded
for completeness.

### Tooling caveat: npm peer-dependency friction
`sonner-native@0.26.4` declares a peer of `react-native-worklets >= 0.6.1` while Expo SDK 54
pins worklets 0.5.1; the combination runs fine (expo-doctor 18/18, bundles compile) but plain
`npm install <anything>` now fails with ERESOLVE. The rule — install new packages with
`npx expo install <pkg> -- --legacy-peer-deps` — is documented in `AGENTS.md`. This is friction
on the easel, not on the painting.

## Verdict

Your mental model is essentially correct: the two big white holes are the **admin overlay** and
**Hyperframes** (the latter leaving seven small, clean cutouts listed above), with **Google
OAuth** and **desktop layouts** as two smaller platform-imposed blanks. Every blackened spot in
the app is a faithful copy of a blackened spot on the website itself (Plans, no-op profile rows,
shared ambassador photo, web-only maintenance form) — the port did not add new placeholders of
its own. The misaligned colors are the nine items in Part 4: one real bug (deep links) found and
fixed during this audit, and eight small platform adaptations/approximations, none of which
break data, state or backend behavior. The final coat of varnish — tapping through
`HUMAN_STEPS.md` Part 3 on a real phone — is yours.
